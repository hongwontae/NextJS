1. NextJS Cache (배포 환경)
1. Request Memoization
=> 동일한 요청(예: fetch 호출)이 동일한 서버 컴포넌트 안에서 여러 번 발생하면, 
이를 한 번만 실행하고 결과를 재사용합니다. (서버 컴포넌트를 감싸고 있는 layout의 fetch 요청도 request Memoization에
해당합니다.)
=> 요청 URL, 옵션(헤더, 메서드 등)이 동일하면 요청 결과를 메모리에 저장하고 재사용합니다.
=> 이는 같은 요청을 중복해서 보내는 것을 방지해 효율성을 높입니다.


2. Data Cache
=> fetch을 통한 요청이 여러 렌더링 주기에서도 발생하더라도 데이터를 다시 가져오지 않고 캐시된 결과를 반환합니다.
=> fetch 함수는 기본적으로 데이터를 캐싱하며, 이 캐시는 요청 URL, 메서드, 헤더를 기준으로 동작합니다.
=> 캐시의 유효 시간을 설정할 수 있고 이 기간이 지나면 다시 가져옵니다.


2-1. Data Cache의 사용 방식
=> fetch 함수의 cache 옵션을 사용하여 Data Cache를 제어할 수 있습니다.

1. cache : 'default' (기본값)
=> 브라우저 캐시, 서버 캐시를 적절하게 사용하는 설정입니다.
=> 브라우저 캐시 HTTP 응답 헤더에 Cache-Control, Etag, Expires 등 캐시 관련 정보가 존재할 떄 캐시합니다.
=> Cache-Control : max-age=3600, 1시간 동안 브라우저가 데이터 캐시

=> 서버 캐시 NextJS가 사용하는 서버 캐시 정책을 사용
=> 서버가 Cache-Control, Etag, Expires 헤더를 보내면 서버 측에서 데이터를 캐시하여 재사용합니다.


2. cache: 'force-cache' (기본값)
=> 데이터를 캐싱하고 재사용.

3. cache : 'no-store' 
=> 데이터를 캐시하지 않고 매 요청마다 새로운 응답을 가지고 옵니다.

4. cache : 'no-cache'
=> 매번 새로운 데이터를 받아야 하지만, no-store보다는 캐시가 존재할 수 있음을 명시하고 싶은 경우 사용합니다.

5. next: { revalidate: n }: 일정 시간(n초)마다 데이터를 갱신.


3. 전역적 Cache 처리

3-1. import {unstable_noStore} from 'next/cache';
=> === export const revalidate = 'no-cache';
=> 해당 설정도 페이지 전반적으로 적용됩니다.
=> 캐시를 아예 사용하지 않도록 설정하는 방법입니다. 
=> 함수를 컴포넌트 내부에서 실행하면 서버 측에서 캐시하지 않게 되며, 매번 요청 시마다 새로운 데이터를 가져옵니다.

3-2. export const revalidation = n;
=> 페이지 단위에서 HTML 갱신 주기를 설정합니다.
=> 해당 페이지 전체의 캐시 갱신 주기를 설정하며, 내부의 개별 fetch 요청과 상관없이 작동합니다.
=> n초가 지나면 백그라운드에서 HTML을 재생성 => 새로운 요청이 올 떄 재생성된 HTML을 반환합니다.

3-3. export const revalidate = n;
=> fetch 요청의 캐싱 동작을 전역적으로 설정합니다.
=> 데이터 갱신 주기만 제어하며, HTML 갱신과는 직접적인 연관이 없습니다.

3-3. revalidation, revalidate는 n초 까지 HTML이나 fetch 데이터를 캐시하고 있다가 n이 지나면 백그라운드에서
새로운 HTML이나 fetch 데이터를 저장하고 새로운 요청이 전달되었을 떄 이 데이터들을 전달하는 매커니즘입니다.
3-4. 위의 세 개의 설정은 하위 컴포넌트까지 영향을 미칩니다.
